# Метрики

[Функция потерь](Функция потерь.md) -  это то, что оптимизируется: по нему считается градиент, он должен быть гладким и дифференцируемым.
Но loss — плохой индикатор 

>Loss (BCE) на тесте = 0.12. Это хорошо или плохо? Непонятно. А вот «из 1000 больных нашли 940, из 1000 здоровых ошибочно записали в больные 30» — понятно сразу. Вот этим и занимаются метрики.

Метрики — это человеко-понятные числа. Они:
- не дифференцируемы
- не участвуют в обучении
- считаются только «на посмотреть»

```java
/**
 * Метрика качества модели. Накапливает статистику по вызовам
 * {@link #update(float[], float[])} и агрегирует её в {@link #result()}.
 * Перед новым прогоном (эпохой/тестом) обязательно вызывается {@link #reset()}.
 * <p>
 * Метрика только <i>измеряет</i> — она не влияет на обучение и не хранится
 * в сериализованной модели.
 */
public interface Metric{
    /** Обработать один пример: prediction — выход сети, target — истина. */
    void update(float[] prediction, float[] target);

    /** Агрегированный результат по всем накопленным примерам. */
    float result();

    /** Сброс накопленной статистики (вызывается перед новым прогоном). */
    void reset();

    /** Имя для логов. */
    String name();
}
```

## Матрица ошибок (confusion matrix)

Прежде чем считать Precision/Recall/F1, полезно понять, **из чего они собираются**. 
Для бинарной классификации есть четыре исхода:

| | Предсказано «положительно» | Предсказано «отрицательно» |
|---|---|---|
| **Реально «положительно»** | TP (True Positive) | FN (False Negative) |
| **Реально «отрицательно»** | FP (False Positive) | TN (True Negative) |

Расшифровка:
- **TP** — больной, и сеть сказала «болен». Правильно.
- **FN** — больной, а сеть сказала «здоров». Пропуск цели (ложноотрицательный).
- **FP** — здоровый, а сеть сказала «болен». Ложная тревога (ложноположительный).
- **TN** — здоровый, и сеть сказала «здоров». Правильно.

Из этой таблицы выводятся **все** базовые метрики:

$$ \text{Accuracy} = \frac{TP + TN}{TP + TN + FP + FN} $$

>Accuracy (доля верных ответов) = (TP+TN)/все — она считает FP и FN одинаково плохими. 
>Но в реальности они часто неравноценны: пропустить болезнь (FN) хуже, чем лишний раз перестраховаться (FP). 
>Поэтому нужны Precision и Recall — они смотрят на разные типы ошибок.

$$ \text{Precision} = \frac{TP}{TP + FP} \quad \text{(«из всех, кого назвали больными, сколько реально больны?»)} $$

> Precision — «насколько точно то, что назвали». Точность.

$$ \text{Recall} = \frac{TP}{TP + FN} \quad \text{(«из всех реально больных, скольких нашли?»)} $$

> Recall — «насколько полно нашли». Полнота

Сеть для бинарной классификации на выходе даёт одно число — вероятность «положительного» класса (после Sigmoid), от 0 до 1. 
Но нам нужно решение: «болен» или «здоров». Число 0.73 — это ещё не ответ.

Порог — это правило перевода вероятности в класс:
```text
prediction >= threshold  →  класс 1 («положительно»)
prediction <  threshold  →  класс 0 («отрицательно»)

По умолчанию берут threshold = 0.5: «больше половины — значит да». Это просто удобное соглашение
```
Порог — отдельная ручка поверх обученной модели. 
Модель уже обучена, её веса не меняются — меняется только точка отсечения. 
И от неё зависят все TP/FP/FN/TN, а значит и Precision/Recall.
Подняли порог → Precision растёт, Recall падает.

Гармоничное среднее(F1)
$$ F_1 = \frac{2 \cdot \text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}} $$

>Почему не обычное среднее? Потому что при P=1, R=0.1 арифметическое среднее = 0.55 — выглядит прилично, хотя модель находит только 10% цели. 
> Гармоническое среднее «тянется» к меньшему: F1 ≈ 0.18. 
> Это честнее: если одна из двух метрик плохая, F1 тоже плохой.

**Многоклассовый случай.** Матрица становится $C \times C$: строки — истинные классы, столбцы — предсказанные. Ячейка $(i, j)$ — сколько примеров класса $i$ сеть отнесла к классу $j$. Диагональ — правильные ответы. Для каждого класса $c$ считают TP/FP/FN **против всех остальных** (one-vs-rest), а потом усредняют:
- **macro** — среднее по классам (все классы равноправны);
- **micro** — суммируем TP/FP/FN по всем классам, потом считаем метрику (крупные классы доминируют);
- **weighted** — среднее с весами по частоте класса.

Пример для 3 классов:

```text
              предсказано
              A    B    C
реально  A [ 50    2    3 ]   ← 55 примеров класса A
         B [  5   40    5 ]   ← 50 примеров класса B
         C [  0    8   42 ]   ← 50 примеров класса C

Accuracy = (50 + 40 + 42) / 155 = 0.852

Для класса A (one-vs-rest):
  TP = 50, FN = 2+3 = 5, FP = 5+0 = 5
  Precision_A = 50 / (50+5) = 0.909
  Recall_A    = 50 / (50+5) = 0.909
  F1_A        = 0.909

macro-F1 = среднее F1 по A, B, C

Зачем смотреть на матрицу, а не только на числа. 
Числа сжимают информацию; матрица показывает структуру ошибок. 
Классический пример: сеть путает классы 3 и 5, но никогда не путает 3 и 7. Accuracy этого не покажет, а матрица — покажет, и вы поймёте, что делать
```

## Accuracy

Доля верных ответов

Применять когда: все ошибки одинаково плохи

Плюсы: интуитивно понятна. Легко сравнивать разные модели.

Минусы:
 - врёт при дисбалансе классов. Если 99% примеров — класс A, модель «всегда A» даст Accuracy = 0.99 и будет бесполезной;
 - не различает типы ошибок. Для медицинской диагностики пропустить больного и ошибочно направить здорового — разные по цене, а Accuracy их складывает.

```java
/**
 * Доля правильных ответов.
 * <ul>
 *   <li>для скалярного выхода (Sigmoid, len == 1) — порог {@code threshold};</li>
 *   <li>для векторного (Softmax, len > 1) — argmax.</li>
 * </ul>
 */
public class Accuracy implements Metric {
    private final float threshold;
    private int correct;
    private int total;

    public Accuracy() { this(0.5f); }
    public Accuracy(float threshold) { this.threshold = threshold; }

    @Override
    public void update(float[] prediction, float[] target) {
        if (classify(prediction) == classify(target)) correct++;
        total++;
    }

    private int classify(float[] arr) {
        if (arr.length == 1) return arr[0] >= threshold ? 1 : 0;
        int best = 0;
        for (int i = 1; i < arr.length; i++) if (arr[i] > arr[best]) best = i;
        return best;
    }

    @Override public float result() { return total == 0 ? 0f : (float) correct / total; }
    @Override public void reset() { correct = 0; total = 0; }
    @Override public String name() { return "Accuracy"; }
}
```

## Precision

Точность

```text
Формула для класса c: TP_c / (TP_c + FP_c)

Где:

TP_c (True Positive) — пример класса c, и сеть сказала c;

FP_c (False Positive) — пример не класса c, а сеть сказала c.

Смысл: «Из всех, кого модель назвала классом c, какая доля действительно c?»
```

Применять когда: ложная тревога дорога. Классика — спам-фильтр: если пометить нормальное письмо как спам (FP), пользователь потеряет важное. Precision тут важнее Recall;

Плюсы: напрямую отвечает на вопрос «насколько можно доверять положительному ответу модели»

Минусы: для многоклассовой задачи macro-усреднение даёт равный вес редким классам, что не всегда нужно

```java
/**Точность.
 * Насколько можно доверять положительному ответу модели?
 *
 * Macro-Precision: среднее TP/(TP+FP) по классам (нулевые — пропускаются). */
public class Precision extends ClassificationStats {
    public Precision() { this(0.5f); }
    public Precision(float threshold) { super(threshold); }

    @Override
    public float result() {
        float sum = 0f; int cnt = 0;
        for (int c = 0; c < numClasses; c++) {
            int denom = tp[c] + fp[c];
            if (denom == 0) continue;
            sum += (float) tp[c] / denom;
            cnt++;
        }
        return cnt == 0 ? 0f : sum / cnt;
    }

    @Override public String name() { return "Precision(macro)"; }
}
```

## Recall

Полнота

```text
Формула для класса c: TP_c / (TP_c + FN_c)

Где FN_c (False Negative) — пример класса c, а сеть сказала что-то другое.

Смысл: «Из всех примеров, которые реально класс c, какую долю сеть нашла?»
```

Применять: когда пропустить цель дорого. Онкология: пропустить опухоль (FN) — катастрофа, а лишняя биопсия (FP) — терпим

Показывает «чувствительность» модели к целевому классу;

Как и Precision, в одиночку легко обманывается.

```java
/**Полнота
 *
 * Из всех примеров, которые реально класс c, какую долю сеть нашла?
 *
 * Macro-Recall: среднее TP/(TP+FN) по классам. */
public class Recall extends ClassificationStats {
    public Recall() { this(0.5f); }
    public Recall(float threshold) { super(threshold); }

    @Override
    public float result() {
        float sum = 0f; int cnt = 0;
        for (int c = 0; c < numClasses; c++) {
            int denom = tp[c] + fn[c];
            if (denom == 0) continue;
            sum += (float) tp[c] / denom;
            cnt++;
        }
        return cnt == 0 ? 0f : sum / cnt;
    }

    @Override public String name() { return "Recall(macro)"; }
}
```

## F1 (macro)

```text
Формула для класса c: 2 · P_c · R_c / (P_c + R_c)

Затем усреднение по классам.

Смысл: гармоническое среднее Precision и Recall — компромисс, который наказывает перекос в любую сторону. Если P = 1, R = 0.1, то F1 ≈ 0.18, а не 0.55 (как было бы у арифметического среднего).
```

Применять при дисбалансе классов, когда Accuracy обманчива

## MAE

Mean Absolute Error

Формула: (1/N) · Σ |y_pred − y_true|

Применять когда присутвуют выбросы в данных и мы не хотим, чтобы они доминировали в оценке

## RMSE

Root Mean Squared Error

Формула: √( (1/N) · Σ (y_pred − y_true)² )

Смысл: тоже в единицах таргета, но сильно штрафует большие ошибки. RMSE ≥ MAE всегда; чем больше разрыв между ними, тем больше в данных крупных выбросов.

MAE vs RMSE — правило выбора:
 - в данных есть выбросы-шум → MAE; 
 - большие ошибки реально катастрофичны → RMSE.

## R2

коэффициент детерминации

```text
Формула: 1 − SS_res / SS_tot, где

SS_res = Σ (y_pred − y_true)²,

SS_tot = Σ (y_true − ȳ)², ȳ — среднее таргета.

Смысл: «какую долю дисперсии таргета объяснила модель по сравнению с тривиальным предсказанием среднего».

R² = 1 — идеальное предсказание;

R² = 0 — модель не лучше константы (среднего);

R² < 0 — модель хуже константы (да, R² может быть отрицательным — это не «процент», а именно коэффициент).
```

Когда применять:
 - регрессия, где важно сравнить модель с «наивным» бейзлайном (средним);
 - когда хочется нормированная метрика, не зависящая от масштаба таргета — можно сравнивать между задачами;

```java
/**
 * Коэффициент детерминации R². Считается по <b>всем</b> значениям всех
 * примеров: 1 — идеальное предсказание, 0 — как константа (среднее),
 * отрицательные значения — хуже среднего.
 *
 * Наказывает за большие ошибки
 */
public class R2 implements Metric {
    private double ssRes;
    private double sumTarget;
    private double sumTargetSq;
    private long n;

    @Override
    public void update(float[] prediction, float[] target) {
        for (int i = 0; i < prediction.length; i++) {
            double d = prediction[i] - target[i];
            ssRes += d * d;
            sumTarget += target[i];
            sumTargetSq += (double) target[i] * target[i];
        }
        n += prediction.length;
    }

    @Override
    public float result() {
        if (n == 0) return 0f;
        double mean = sumTarget / n;
        double ssTot = sumTargetSq - n * mean * mean;
        if (ssTot <= 1e-12) return 0f;
        return (float) (1.0 - ssRes / ssTot);
    }

    @Override public void reset() { ssRes = 0; sumTarget = 0; sumTargetSq = 0; n = 0; }
    @Override public String name() { return "R2"; }
}
```

| Вопрос | Метрика |
| --- | --- |
| Какая средняя ошибка в единицах таргета? | MAE |
| Насколько страшны крупные промахи? | RMSE |
| Насколько модель лучше, чем «всегда среднее»? | R² |

RMSE ≥ MAE всегда, разрыв = «вес хвостов».

## Практические рекомендации

- Всегда считайте Accuracy + F1 вместе для классификации. Accuracy даёт «общую картину», F1 — «честную картину на дисбалансе». Если они сильно расходятся — в данных дисбаланс, и Accuracy обманчива.
- Precision и Recall — смотрите парой. Если Precision = 0.95, а Recall = 0.3 — модель почти всегда права, когда отвечает, но упускает 70% цели. Одна цифра без другой ничего не значит.
- Для регрессии — MAE + RMSE + R². MAE даёт «среднюю ошибку в единицах», RMSE — «масштаб крупных промахов», R² — «насколько лучше константы». Разрыв MAE и RMSE показывает, есть ли тяжёлые хвосты в ошибках.
- Threshold — не всегда 0.5. В Accuracy(threshold) можно поднять порог: если вам важнее не ошибиться в «положительных» (высокий Precision), ставьте 0.7–0.8. Если важнее всех поймать (высокий Recall) — 0.2–0.3. Метрика и порог — два независимых рычага.
- Метрика ≠ Loss. Не пытайтесь оптимизировать Accuracy напрямую (не дифференцируема). Обучайте по CrossEntropy/MSE, а метрикой только измеряйте. Исключение — специальные «surrogate»-loss’ы, но это отдельная тема.
- Смотрите метрику на нескольких эпохах, а не только в конце. Если Accuracy растёт, а F1 падает — модель «скатывается» к доминирующему классу. В коде метрики уже логируются на каждой контрольной эпохе (см. train).
- Не сравнивайте MAE/RMSE между задачами — они в единицах таргета. R² и Accuracy/F1 — сравнимы, они безразмерны.

## LossMetric

Обёртка над Loss как Metric.

```java
/**
 * Обёртка над {@link Loss}, представляющая её как {@link Metric}.
 *
 * <h2>Зачем</h2>
 * {@link Metric} считают метрики (RMSE, accuracy, F1, ...), а {@link Loss} —
 * функцию, которую <i>оптимизирует</i> сеть. Это разные вещи, и полезно
 * видеть обе на одной выборке одновременно:
 * <ul>
 *   <li>loss падает, а метрика нет → метрика плохо согласована с задачей
 *       (например, RMSE усредняет поля с разной семантикой);</li>
 *   <li>loss не падает → проблема в модели/данных/гиперпараметрах;</li>
 *   <li>loss и метрика падают согласованно → всё в порядке.</li>
 * </ul>
 *
 * <h2>Использование</h2>
 * <pre>{@code
 * Loss loss = new DetectionLoss(maxDet, numClasses);
 * model.train(epochs, ds, loss, opt, batchSize, 3,
 *         List.of(new Rmse(), new LossMetric(loss)), null);
 * // В логе: "RMSE=0.14  Loss(DetectionLoss)=0.031"
 * }</pre>
 *
 * <h2>Переиспользование</h2>
 * Работает с <b>любой</b> реализацией {@link Loss}: MSE, BCE, MAE,
 * SoftmaxCrossEntropy, DetectionLoss — без изменений. Не знает о структуре
 * выхода (плоский вектор / слоты / что угодно), просто вызывает
 * {@code loss.loss(p, t)}. Никакого состояния между вызовами, кроме счётчика.
 */
public class LossMetric implements Metric {
    private final Loss loss;
    private double sum;
    private int n;

    public LossMetric(Loss loss) {
        this.loss = Objects.requireNonNull(loss, "loss");
    }

    @Override
    public void update(float[] prediction, float[] target) {
        sum += loss.loss(prediction, target);
        n++;
    }

    @Override
    public float result() { return n == 0 ? 0f : (float) (sum / n); }

    @Override
    public void reset() { sum = 0; n = 0; }

    @Override
    public String name() { return "Loss(" + loss.getClass().getSimpleName() + ")"; }
}
```
