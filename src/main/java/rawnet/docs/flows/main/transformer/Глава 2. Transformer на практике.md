Сценарии использования

Seq2seq — это энкодер + декодер с cross-attention и teacher forcing. Самая полная сборка Transformer'а: две ветви, три механизма (causal, cross, teacher forcing), авторегрессионная генерация.

BERT (убрать декодер) 

GPT (убрать энкодер и cross-attention). 

Все три — один и тот же Transformer, но с разной обвязкой.



##  Seq2seq-перевод: энкодер + декодер

Sequence-to-Sequence — «последовательность в последовательность». 
Это класс моделей, которые преобразуют одну последовательность в другую, возможно, другой длины.

[Seq2SeqExample](tasks/Seq2SeqExample.java)

Классический seq2seq: на входе — последовательность на одном языке, на выходе — на другом. 
Длина входа Tkv и выхода Tq могут различаться. 
Это самая полная сборка Transformer'а: EncoderStack + DecoderBlock + голова + SequenceCrossEntropy.

```text
ВХОД (source):  flat(Tkv) индексов                                ←  Энкодер
  │
  ▼ MaskingLayer(PAD)
  ▼ EmbeddingLayer(vocab_src, dModel)
  ▼ PositionalEncodingLayer
  ▼ TransformerEncoderStack (N блоков + LN)
  │
  ▼ encOut: seq(Tkv, dModel)
       │
       │   (идёт как KV в декодер)
       ▼
ВХОД (target):  flat(Tq) индексов                                  ←  Декодер
  │
  ▼ MaskingLayer(PAD)
  ▼ EmbeddingLayer(vocab_tgt, dModel)
  ▼ PositionalEncodingLayer
  ▼ TransformerDecoderBlock × M       ← Q = target, KV = encOut
  │
  ▼ seq(Tq, dModel)
  ▼ TimeDistributedDense(vocab_tgt)
  │
  ▼ logits: seq(Tq, vocab_tgt)
  │
  ▼ SequenceCrossEntropy (обучение)
```

```text
Encoder:
  flat(SRC_LEN)  →  Masking  →  Embedding  →  PE  →  Stack(N)  →  seq(SRC_LEN, dModel)

Decoder:
  flat(TGT_LEN)  ─┐
                  ├─→ Embedding → PE → DecoderBlock(M) → TD-Dense(vocab) → seq(TGT_LEN, vocab)
  seq(SRC_LEN, dModel) ─┘ (KV)
```

Две ветви, одна точка связи. Энкодер читает source, декодер пишет target. 
Единственная связь между ними — encOut: выход энкодера идёт как KV в cross-attention декодера. 
Всё остальное — независимые ветви.

```java
Functional.Builder b = Functional.builder(
        TensorShape.flat(SRC_LEN),   // src — индексы
        TensorShape.flat(TGT_LEN));  // tgt — индексы (сдвинутые)

Functional.Node srcIn = b.input();     // Q-ветвь
Functional.Node tgtIn = b.kvInput();   // KV-ветвь
```

Названия input/kvInput — исторические (от cross-attention), но здесь они означают просто «первый вход» и «второй вход». В seq2seq первый — source, второй — target.

### Ветвь энкодера

Стандартная BERT-подобная сборка, только без головы:
```java
Functional.Node srcMask = b.layer(new MaskingLayer.Dto(PAD), srcIn);
Functional.Node srcEmb  = b.layer(new EmbeddingLayer.Dto(srcVocab.size(), D_MODEL), srcMask);
Functional.Node srcPe   = b.layer(new PositionalEncodingLayer.Dto(), srcEmb);
Functional.Node encOut  = TransformerEncoderStack.build(b, srcPe, new TransformerEncoderBlock.Dto(HEADS, D_MODEL, D_FF, DROPOUT, false), N_ENC);
```

MaskingLayer(PAD) строит маску: 1 — настоящий токен, 0 — PAD. Она пробрасывается через Embedding и PE (нейтральные слои) и доходит до TransformerEncoderStack, где MultiHeadAttentionLayer её читает — PAD-ключи исключаются из softmax.

encOut — это seq(SRC_LEN, dModel), та же форма, что и вход, но с «обогащёнными» векторами: каждый токен теперь содержит информацию обо всей source-фразе через self-attention.

[блок-transformerа-энкодер](Глава%2010.%20Механизм%20внимания%20и%20Transformer.md#блок-transformerа-энкодер)

### Ветвь декодера

```java
Functional.Node tgtMask = b.layer(new MaskingLayer.Dto(PAD), tgtIn);
Functional.Node tgtEmb  = b.layer(new EmbeddingLayer.Dto(tgtVocab.size(), D_MODEL), tgtMask);
Functional.Node tgtPe   = b.layer(new PositionalEncodingLayer.Dto(), tgtEmb);

Functional.Node dec = tgtPe;
for (int i = 0; i < N_DEC; i++) {
    dec = TransformerDecoderBlock.build(b, dec, encOut,new TransformerDecoderBlock.Dto(HEADS, D_MODEL, D_FF, DROPOUT, SRC_LEN));
}
```

[TransformerDecoderBlock](Глава%2010.%20Механизм%20внимания%20и%20Transformer.md#блок-transformerа-декодер) — это три подслоя, а не два, как в энкодере:
- Causal self-attention — токен t видит только 0..t-1 (не подглядывает в будущее). causal=true обязателен: без него модель на обучении «подсмотрит» target на позиции t, loss упадёт до нуля, а на инференсе всё развалится.
- Cross-attention — Q из декодера, KV из encOut. Здесь декодер «смотрит» на source: для каждого target-токена attention находит, на какие source-токены обратить внимание.
- FFN — обработка каждого токена отдельно.

Почему cross-attention, а не «просто два энкодера»? 
Потому что декодер должен сопоставить target-токены с source-токенами. 
На шаге генерации «мир» (target) декодер должен понять, что это перевод «world» (source). 
Cross-attention позволяет: Q — это «мир» (что я ищу), K — это все source-токены (где искать), V — их значения. 
Softmax выделяет world, и Y для «мир» содержит информацию о «world».

Без cross-attention декодер был бы «слепым»: он видел бы только свой префикс, но не source. 
Это как переводить, не глядя в исходный текст.

После каждого — residual + LayerNorm (pre-LN). 

kvLen = SRC_LEN — длина encOut, нужна для проверки формы.

### Голова и loss

```java
Functional.Node logits = b.layer(new TimeDistributedDenseLayer.Dto(tgtVocab.size()), dec);
return b.output(logits);
```

TimeDistributedDense(vocab_tgt) применяет одну матрицу [vocab_tgt][dModel] к каждому из TGT_LEN токенов независимо. Выход — seq(TGT_LEN, vocab_tgt) — сырые логиты, не вероятности.

SequenceCrossEntropy принимает логиты: softmax считается внутри, по каждой позиции отдельно. SoftmaxCrossEntropy здесь не подходит — он трактует вход как один вектор логитов, а не TGT_LEN векторов.

### Teacher forcing

Ключевой момент seq2seq: на позиции t декодер получает токены 0..t-1, а предсказывает токен t.

```java
int[] tgtIn  = encode(p[1], tgtVocab, TGT_LEN, true);   // BOS + слова + EOS
int[] tgtOut = shiftLeft(tgtIn);                        // слова + EOS + PAD
out.add(new NInputSample(
        new float[][]{ toFloat(src), toFloat(tgtIn) },  // декодер видит
        toFloat(tgtOut)));                              // loss на след. токене
```

tgtIn = [BOS, w0, w1, ..., EOS, PAD, ...] — вход декодера. tgtOut = [w0, w1, ..., EOS, PAD, PAD] — сдвиг на 1, target для loss. На позиции 0 logits[0] (декодер видел только BOS) должен предсказать tgtOut[0] = w0. На позиции 1 logits[1] (видел BOS, w0) — w1. И так далее.

causal=true в self-attention гарантирует, что позиция t не подсмотрит токен t+1 в target — иначе модель «списала» бы ответ, и на инференсе (где будущих токенов нет) развалилась бы.

Почему это называется teacher forcing. На обучении мы подаём настоящий сдвинутый target, а не то, что декодер сам сгенерировал. 
Это «учитель», который «подсказывает» правильную последовательность на каждом шаге.

Почему это не читерство? 
Потому что causal-маска гарантирует: на позиции t декодер видит только 0..t-1, а предсказывает t. 
Он не видит tgtOut[t] (будущий токен) — он видит только tgtIn[t] (прошлые). 
Teacher forcing подаёт прошлые токены, а не будущие. 
Causal-маска не даёт «подсмотреть» tgtOut[t] — иначе модель «списала» бы ответ, и на инференсе (где будущего нет) развалилась бы.

В последовательностях разной длины PAD заполняет хвост. 
Без маски модель «учится предсказывать PAD» на PAD-позициях — это шум, который мешает градиенту от полезных токенов.

SequenceCrossEntropy и TokenAccuracy реализуют MaskAcceptLoss/MaskAcceptMetric — опциональные интерфейсы с маской:

ModelTraining строит маску mask[t] = (target[t] == PAD) ? 0 : 1 и передаёт в lossMasked/updateMasked. Loss на PAD-позициях = 0, градиент = 0. Метрика TokenAccuracy тоже считает только валидные позиции — иначе она «раздувается» за счёт угадывания PAD.

TokenAccuracy — argmax по каждой позиции отдельно, сравнение с target.

```text
Как teacher forcing связан с инференсо

Обучение и инференс — **одна и та же операция** (предсказать следующий токен по прошлым), но с **разным источником** прошлых токенов.

Обучение (teacher forcing):
  tgtIn  = [BOS, кот, EOS, PAD]
  tgtOut = [кот, EOS, PAD, PAD]

  Позиция 0: декодер видит [BOS],             предсказывает "кот"   (tgtOut[0])
  Позиция 1: декодер видит [BOS, кот],        предсказывает "EOS"   (tgtOut[1])
  Позиция 2: декодер видит [BOS, кот, EOS],   предсказывает "PAD"   (tgtOut[2])

  Прошлые токены — из tgtIn (настоящий target). Это «учитель подсказывает».

Инференс (автoreгрессия):
  prefix = [BOS]

  Шаг 1: декодер видит [BOS],             предсказывает "кот"  → prefix = [BOS, кот]
  Шаг 2: декодер видит [BOS, кот],        предсказывает "EOS"  → prefix = [BOS, кот, EOS]
  Шаг 3: "EOS" → стоп.

  Прошлые токены — из prefix (то, что декодер сам сгенерировал). Это «модель идёт сама».
  
teacher forcing — это **симуляция инференса**, но с «подсказками». Causal-маска делает симуляцию **честной** (не даёт подсмотреть), а teacher forcing — **стабильной** (не даёт ошибкам накапливаться на обучении)  
```

### Авторегрессионная генерация

Обученный декодер умеет предсказывать следующий токен по префиксу. 
Чтобы сгенерировать всю последовательность, нужно повторять это Tq раз: на каждом шаге подать текущий префикс, взять argmax, добавить токен, повторить.

```text
1. prefix = [<s>]                          (start token)
2. пока не <e> и len(prefix) < maxLen:
     logits = decoder.forward2(prefix, encOut, false)   → seq(len, vocab)
     last   = logits[последняя позиция]                  → vocab логитов
     next   = argmax(last)
     prefix = prefix + [next]
3. вернуть prefix[1:]                       (без <s>)

где <s>-токен начала (start), а <e>-токен конца (end)
```

```java
int[] prefix = new int[TGT_LEN];
prefix[0] = BOS;
int len = 1;
while (len < TGT_LEN) {
    int[] tgtPadded = Arrays.copyOf(prefix, TGT_LEN);
    float[] logits = model.forward2(toFloat(srcPadded), toFloat(tgtPadded), false);

    int off = (len - 1) * vocabSize;
    int best = argmax(logits, off, vocabSize);

    if (best == EOS || best == PAD) break;   // стоп
    prefix[len++] = best;
}
```

Без KV-cache attention пересчитывается по всему префиксу на каждом шаге — O(len²) на шаг, O(Tq³) на всю генерацию. Для Tq = 10 — миллисекунды. В продакшене — KV-cache: K и V для уже обработанных токенов сохраняются между шагами, и на новом шаге считается только Q для нового токена. Это даёт O(Tq) на шаг. В библиотеке KV-cache не реализован (требуется инкрементальный forward) — для понимания механики он не нужен, но знать о нём важно.

###  Поиск

Жадная генерация выбирает один лучший токен на каждом шаге. 
Если модель «сворачивает» на частый шаблон (например, EOS вместо объекта), жадная генерация ошибётся. 
Beam search держит k лучших гипотез по сумме log-prob и в конце выбирает лучшую:

```java
private static int[] beamTranslate(Functional model, int[] src, Vocab tgtVocab, int beamWidth) {
    // beam — список гипотез (префикс + сумма log-prob + завершена ли)
    // на каждом шаге: расширяем все незавершённые гипотезы,
    //                 сортируем по длине-нормированному log-prob,
    //                 берём top-k
    // в конце: лучшая по нормированному log-prob
}
```

Почему log-prob, а не вероятности. Произведение вероятностей уходит в 0 для длинных последовательностей. Сумма логарифмов — стабильна и аддитивна.
>Log-prob (логарифм вероятности) — это log(p), где p — вероятность события (число от 0 до 1). В контексте beam search и вообще языковых моделей это стандартный способ складывать вероятности шагов вместо того, чтобы их умножать.

Length penalty. Без неё beam search предпочитает короткие гипотезы (у них больше средняя вероятность на токен). Деление на len^α с α = 0.6 — компромисс.

Когда помогает, когда нет. 
На хорошо обученной модели beam search находит варианты, которые жадная пропускает (например, «кот читает книгу» vs «кот читает письмо» — обе правдоподобны, но одна правильная). 
На недоученной — не помогает: модель уверена в неправильном (например, EOS после boy drinks), и beam search выбирает то же, что жадная.
```text
Недоученная модель, "the boy drinks the milk":
  P(EOS | boy drinks) = 0.9
  P(milk | boy drinks) = 0.05
  P(water | boy drinks) = 0.03
  ...

Жадная: выбирает EOS (0.9) → "boy drinks" (обрезано).
Beam(3): держит 3 гипотезы:
  "boy drinks EOS"     (0.9)
  "boy drinks milk"    (0.05)
  "boy drinks water"   (0.03)
  
  Все 3 гипотезы продолжаются, но EOS-гипотеза «выигрывает» по сумме log-prob:
  log(0.9) = -0.1
  log(0.05) = -3.0
  log(0.03) = -3.5
  
  Beam выбирает "boy drinks EOS" — то же, что жадная.
  
Beam search полезен, когда P(EOS) и P(milk) **близки** (например, 0.4 vs 0.35) — тогда beam может найти «milk» через продолжение. Но если P(EOS) = 0.9, beam бессилен: модель «уверена» в неправильном.
```

### Смотрим что получилось

Корпус: 200 пар EN → RU, сгенерированных комбинаторно (subject × verb × object, 6 × 4 × 10 = 240 минус «невозможные» и минус held-out). Модель: D_MODEL = 64, HEADS = 8, N_ENC = N_DEC = 2, DROPOUT = 0.1, EPOCHS = 100, BATCH = 8, LR = 3e-3.

```text
Train: 180, Test: 20
Эпоха 0:  TokenAccuracy=0.4000
Эпоха 5:  TokenAccuracy=0.8500
Эпоха 10: TokenAccuracy=0.9625
Эпоха 15: TokenAccuracy=1.0000
Эпоха 100: TokenAccuracy=1.0000
```

TokenAccuracy = 1.0 на train — модель выучила все 180 пар. Test (20 пар из того же корпуса) — тоже 1.0.

```text
EN: the cat eats the bread     RU: кот ест хлеб
EN: the dog eats the bird      RU: собака ест птицу
EN: the boy eats the flower    RU: мальчик ест цветок
EN: the boy sees the bird      RU: мальчик видит птицу
EN: the dog drinks the book    RU: собака читает книгу   ← путаница глагола
```

4 из 5 идеально. Одна ошибка (drinks → читает) — модель видела dog drinks и dog reads, но не dog drinks book (это редкость — собаки не пьют книги). 
В test-выборке такая пара есть, и модель выбрала более частый глагол читает. 
Это разумная ошибка.

Held-out (фразы, которых нет в train):
```text
EN: the woman sees the cat
   ожидалось: женщина видит кота
   greedy   : женщина видит кота         ✓
   beam(3)  : женщина видит кота         ✓

EN: the man reads the letter
   ожидалось: человек читает письмо
   greedy   : человек читает письмо      ✓
   beam(3)  : человек читает письмо      ✓

EN: the cat reads the book
   ожидалось: кот читает книгу
   greedy   : кот читает книгу           ✓
   beam(3)  : кот читает книгу           ✓

EN: the boy drinks the milk
   ожидалось: мальчик пьет молоко
   greedy   : мальчик пьет               ✗ (без объекта)
   beam(3)  : мальчик пьет               ✗

EN: the girl sees the boy
   ожидалось: девочка видит мальчика
   greedy   : девочка видит              ✗ (без объекта)
   beam(3)  : девочка видит              ✗

EN: the woman sings the song
   ожидалось: женщина поет песню
   greedy   : женщина читает кота        ✗ (sings/song → <unk>)
   beam(3)  : женщина читает кота        ✗
```

Модель выучила структуру. Порядок «subject — verb — object» — идеально. Согласование — на месте. Словарь — выучен (cat→кот, dog→собака, woman→женщина, reads→читает, drinks→пьёт, book→книгу, …).

Модель обобщает на новые комбинации. the woman sees the cat — не было в train (held-out), но модель перевела точно: woman→женщина и cat→кота она видела в других комбинациях, и cross-attention собрал их вместе.

Две фразы обрезаны — и это объяснимо. the boy drinks the milk и the girl sees the boy — не в train (они в held-out). В train были boy drinks (с другими объектами) и milk (с другими субъектами), но не boy drinks milk. Модель не уверена, что после boy drinks идёт именно milk, и сворачивается на EOS. Это не баг, а ограничение: модель интерполирует между виденными парами, но не экстраполирует на принципиально новые комбинации.
>Решения
> - minLength в beam search — не останавливаться на EOS слишком рано
> - length penalty в beam search — сильнее наказывать короткие (Сейчас α = 0.6. Если увеличить до α = 1.0)
> - EOS penalty — штрафовать EOS при генерации (Простой трюк: при вычислении log p для EOS вычесть фиксированный штраф (например, -2.0), чтобы модель реже выбирала EOS. Это искусственно заставляет продолжать.)

Beam search не помогает на этих двух. Все гипотезы в beam имеют одинаковую проблему: boy drinks → EOS с высокой вероятностью, boy drinks milk — с низкой. Beam search выбирает то, что модель считает вероятным, а не то, что правильно. Он полезен, когда модель уверена в нескольких вариантах и нужно выбрать лучший, — но не когда модель не уверена в правильном.

<unk> — правильно. sings/song вне словаря → <unk>. Модель подставляет знакомые слова (читает кота) — это лучше, чем <unk> <unk>, но не перевод. Нельзя перевести слово, которого не знаешь.

Правило большого пальца:
- Мало данных (< 50 пар) → DROPOUT = 0, EPOCHS = 40–100, модель выучит шаблон.
- Достаточно данных (100–500 пар) → DROPOUT = 0.1, EPOCHS = 100–200, модель выучит все комбинации и будет обобщать.
- Много данных (> 1000 пар) → DROPOUT = 0.1–0.2, EPOCHS = 200+, модель выучит язык, а не только структуру.


## BERT-style классификатор

Bidirectional Encoder Representations from Transformers — «двунаправленные представления энкодера на основе Трансформера» .

Главная идея: глубокая двунаправленность

До BERT модели вроде word2vec давали статичные векторы: слово «bank» имело один и тот же вектор в «bank account» и «river bank». BERT же генерирует контекстные представления: вектор слова зависит от всего предложения .

BERT использует только энкодер из архитектуры Трансформера .
В нашей главе это ровно то, что мы собирали: TransformerEncoderStack + голова. 
BERT не умеет генерировать текст (для этого нужен декодер, как в GPT), его задача — понимать текст и создавать его векторное представление.

Почему BERT не может генерировать? 
Потому что у него нет causal-маски: он видит всю последовательность сразу (и левый, и правый контекст). 
Это хорошо для понимания, но плохо для генерации: на шаге t BERT «видит» t+1, t+2, ... — и не может их предсказать, потому что он их уже «знает».

GPT — наоборот: causal-маска не даёт видеть будущее, и он вынужден предсказывать следующий токен по прошлым. Это и есть генерация.

Обучить двунаправленную модель «предсказывать следующее слово» нельзя — она бы просто «подсмотрела» ответ. Поэтому Google придумал два трюка:
- Masked Language Modeling (MLM): Мы прячем (маскируем) некоторые слова в предложении (например, 15%) и просим модель их восстановить, глядя на весь оставшийся контекст. Только так можно научить модель смотреть в обе стороны .
- Next Sentence Prediction (NSP): Модель получает пару предложений A и B и учится определять, является ли B реальным следующим предложением в тексте или случайным .

При работе с BERT важно помнить про его «служебные» токены :
- [CLS]: Ставится в начало каждой последовательности. Его итоговый вектор после энкодера используется как агрегированное представление всей фразы для задач классификации. Именно его мы брали через TokenPoolingLayer(Mode.FIRST).
- [SEP]: Разделитель, если на вход подаётся пара предложений (например, вопрос и ответ).

В нашей задаче мы научим BERT классифицировать отзывы о фильмах на позитивный/негативный.

[BertClassifierExample](../code/task/transform/BertClassifierExample.java) - классификатор отзывов с токенизацией по словам

[Bpe](../code/task/transform/Bpe.java) -Byte Pair Encoding — «кодирование парами байтов».

[BertClassifierExampleWithBpe](../code/task/transform/BertClassifierExampleWithBpe.java) - тот же классификатор с токенизацией через BPE

BERT — это только энкодер + голова. На вход — последовательность токенов, на выход — класс. 
Один из самых распространённых сценариев: классификация текста, NER, sentiment.

```text
ВХОД:  flat(T) индексов
  │
  ▼ MaskingLayer(PAD)
  ▼ EmbeddingLayer(vocab, dModel)
  ▼ PositionalEncodingLayer
  ▼ TransformerEncoderStack (N блоков + LN)
  │
  ▼ seq(T, dModel)
  ▼ TokenPoolingLayer(Mode.FIRST)        ← берём [CLS]-токен
  ▼ flat(dModel)
  ▼ DenseLayer(numClasses)               ← логиты
  ▼ (SoftmaxCrossEntropy)
```

В BERT на позицию 0 ставится специальный токен [CLS]. 
После энкодера его выход — агрегированное представление всей последовательности (он «видел» все токены через attention). 
TokenPoolingLayer(Mode.FIRST) берёт именно его. MEAN тоже работает (и часто не хуже), но FIRST — стандарт BERT, и он даёт модели «выделенную» позицию для агрегации.

Почему только энкодер

В seq2seq нужны две ветви: энкодер читает source, декодер пишет target. 
Для классификации target — один класс, а не последовательность. 
Значит, декодер не нужен: энкодер «сжимает» последовательность в один вектор, голова классифицирует.
```text
BERT-классификатор = EncoderStack + голова
Seq2seq           = EncoderStack + DecoderStack + голова
GPT (LM)          = DecoderStack + голова
```

```java
Functional.Builder b = Functional.builder(TensorShape.flat(SEQ_LEN));
Functional.Node in = b.input();

// ---------- Энкодер ----------
Functional.Node mask = b.layer(new MaskingLayer.Dto(PAD), in);
Functional.Node emb  = b.layer(new EmbeddingLayer.Dto(vocab.size(), D_MODEL), mask);
Functional.Node pe   = b.layer(new PositionalEncodingLayer.Dto(), emb);
Functional.Node enc  = TransformerEncoderStack.build(b, pe, new TransformerEncoderBlock.Dto(HEADS, D_MODEL, D_FF, DROPOUT, false), N_ENC);

// ---------- Голова: [CLS] → Dense ----------
Functional.Node pooled = b.layer(new TokenPoolingLayer.Dto(TokenPoolingLayer.Mode.FIRST), enc);

Functional.Node logits = b.layer(new DenseLayer.Dto(TensorShape.flat(NUM_CLASSES)), pooled);

return b.output(logits);
```
**MaskingLayer(PAD) — источник маски**

MaskingLayer строит маску float[T]: 1 — настоящий токен, 0 — PAD. Она пробрасывается через нейтральные слои (Embedding, PE, EncoderStack) и доходит до MultiHeadAttentionLayer, где PAD-ключи исключаются из softmax. Без маски модель «смотрит» на PAD-позиции, и attention тратит ёмкость на шум.

**EmbeddingLayer(vocab, dModel) — таблица поиска**

flat(T) индексов → seq(T, dModel) векторов. Каждый токен — обучаемый вектор длины dModel. Обучается вместе со всей моделью — это не «замороженные» word2vec-эмбеддинги, а часть сети, оптимизируемая под задачу классификации.

**PositionalEncodingLayer — позиции**

Transformer не имеет рекуррентности — без позиционного кодирования модель не различает «кот видит собаку» и «собака видит кота». PE добавляет к каждому вектору синусоидальный сигнал, зависящий от позиции t и размерности i. Это не обучаемые параметры — фиксированная формула.

**TransformerEncoderStack(N) — N блоков + LN**

N блоков подряд. Каждый — self-attention + FFN + residual + LayerNorm (pre-LN). TransformerEncoderStack добавляет финальный LayerNorm после всех блоков: в pre-LN выход последнего блока не нормирован, и голова получила бы сигнал с большим разбросом.

causal = false — для классификации не нужно causal-маски: модель видит всю последовательность целиком. causal = true — только для авторегрессии (GPT).

**TokenPoolingLayer(FIRST) — берём [CLS]**

Вход — seq(T, dModel), выход — flat(dModel). Mode.FIRST берёт выход позиции 0 — это [CLS]-токен. Он «видел» все токены через self-attention и накопил агрегат. MEAN (среднее по всем токенам) — альтернатива, тоже работает, но FIRST — стандарт BERT.

**DenseLayer(numClasses) — голова**

flat(dModel) → flat(numClasses). Для бинарной классификации numClasses = 2: [logit_neg, logit_pos]. Выход — сырые логиты, не вероятности. SoftmaxCrossEntropy применит softmax внутри.

[CLS] на позиции 0

```java
private static int[] encode(String text, Vocab vocab) {
    int[] out = new int[SEQ_LEN];
    Arrays.fill(out, PAD);
    out[0] = CLS;                        // <-- [CLS] всегда на позиции 0
    int pos = 1;
    Matcher m = TOKEN.matcher(text);
    while (m.find() && pos < SEQ_LEN) {
        out[pos++] = vocab.idx(m.group().toLowerCase(Locale.ROOT));
    }
    return out;
}
```

Vocab резервирует три спец-токена в фиксированном порядке:
```java
private static final int PAD = 0;
private static final int CLS = 1;
private static final int UNK = 2;
```

[CLS] — это обучаемый токен, как и любое слово. Его embedding инициализируется случайно и оптимизируется вместе со всей моделью. После энкодера его выход — «сводка» всей фразы, и Dense классифицирует именно её.

### Loss и метрика

```java
SoftmaxCrossEntropy loss = new SoftmaxCrossEntropy();
List<Metric> metrics = List.of(new Accuracy());
```
SoftmaxCrossEntropy принимает логиты [logit_neg, logit_pos] и one-hot target [1, 0] или [0, 1]. Softmax считается внутри, по всему вектору — это один softmax на фразу, а не T softmax, как в SequenceCrossEntropy.

Accuracy делает один argmax по вектору [neg, pos] и сравнивает с argmax target. Для seq2seq нужна TokenAccuracy (argmax по каждой позиции), но здесь позиция одна — классификация.

### Токенизация: слово vs BPE

Можно разбивать текст по словам
```java
private static final Pattern TOKEN = Pattern.compile("[\\p{L}']+", Pattern.UNICODE_CHARACTER_CLASS);
```
Каждое слово — один токен. Для 88 фраз про фильм это работает: словарь ~60 слов, модель выучивает хороший/плохой как positive/negative.

Проблема: слова вне словаря → <unk>. «Восхитительная» (женский род) не в словаре (в train только «восхитительный», мужской) → <unk> → Dense не имеет сигнала → уверенно врёт (выдаёт POSITIVE 1.00 из-за bias, а не из-за сигнала).

Решение: BPE-токенизация. Слова разбиваются на общие куски: «восхитительная» → восхи + т + и + тель + ная. Префикс восхи есть в train (из «восхитительный») → Dense видит сигнал → классифицирует осмысленно.

>Почему word-level «ломается»? Потому что словарь фиксирован: если слова нет в словаре, оно всегда <unk>. 
> «Восхитительная» — это новая форма (женский род), и в словаре её нет. 
> Модель не может «догадаться», что это форма от «восхитительный» — для неё это просто <unk>, как и любое другое незнакомое слово.
>
>BPE решает это принципиально: он разбивает слово на знакомые куски (восхи + т + и + тель + ная). 
> Даже если целого слова нет в словаре, его куски — есть. И модель может «собрать» смысл из кусков.

### BPE своими руками

Byte Pair Encoding = «кодирование парами байтов». 
Название — от оригинального алгоритма сжатия (1994). 
В NLP — тот же алгоритм, но для токенизации: сливаем частые пары символов (или байтов) в новые токены, пока не наберём словарь нужного размера.

[Bpe](../code/task/transform/Bpe.java)

1. Инициализация. Каждое слово — символы + </w> (маркер конца).
2. Подсчёт пар. По корпусу считаются частоты пар соседних символов.
3. Слияние. Самая частая пара сливается в новый токен.
4. Повтор. Шаги 2–3, пока словарь не достигнет vocabSize.

```java
// в Bpe.train
while (bpe.vocab.size() < vocabSize) {
    Map<String, Integer> pairFreq = new HashMap<>();
    for (var e : splits.entrySet()) {
        List<String> chars = e.getKey();
        int freq = e.getValue();
        for (int i = 0; i < chars.size() - 1; i++) {
            pairFreq.merge(chars.get(i) + "\0" + chars.get(i + 1), freq, Integer::sum);
        }
    }
    // самая частая пара → merged → добавляем в vocab
}
```

>"\0" — это разделитель между двумя символами пары. Без него была бы коллизия: разные пары давали бы одну и ту же строку.
> ```text
> Пара 1: left="а",  right="бв"  → склеиваем как "абв"
> Пара 2: left="аб", right="в"   → склеиваем как "абв"
> 
> "абв" — одна и та же строка, но это две разные пары! (а, бв) и (аб, в) — разные, а ключ в HashMap — один. pairFreq.merge("абв", freq, sum) склеит их частоты, и BPE неправильно посчитает, какая пара самая частая.
> Поэтому разделяем через \0
>```

Кодирование применяет merges в том же порядке, в котором они появились при обучении:
```java
// в Bpe.encodeWord
for (String[] merge : merges) {
    // проходим по слову, сливаем пары merge[0] + merge[1]
}
```
Почему порядок критичен. BPE применяет правила последовательно. 
Если [х, о] появилось раньше [хо, р], то «хор» → хо + р, а не х + ор. 
Это не баг, а свойство BPE: пары накапливаются в определённом порядке, и при кодировании нужно соблюдать его.


Без BPE (BertClassifierExample)
```text
Словарь: 62 слов
...
"картина была восхитительная"  → POSITIVE (pos=1.00, neg=0.00)  ← <unk>, bias
"картина была кошмарная"       → POSITIVE (pos=1.00, neg=0.00)  ← <unk>, bias
```

восхитительная и кошмарная → <unk>. Модель видит [CLS, <unk>, <unk>, <unk>, PAD...] — только картина и была знакомы, и они нейтральны. Dense выдаёт случайный, но уверенный ответ (bias склонился к positive). 
Обе фразы → POSITIVE — и это неправильно для кошмарная.

С BPE (BertClassifierExampleWithBpe)
```text
BPE: Bpe{vocab=264, merges=233}
...
"картина была восхитительная"  → POSITIVE (pos=1.00, neg=0.00)  ✓
     pieces: [картина</w>, была</w>, восхитительная</w>]
"картина была кошмарная"       → NEGATIVE (pos=0.00, neg=1.00)  ✓
     pieces: [картина</w>, была</w>, кошм, ар, ная</w>]
```

восхитительная → целое слово. BPE слил его целиком, потому что в train есть "это восхитительная картина" (мы добавили female-форму). Dense выучил восхитительная → positive, и модель уверена.

кошмарная → кошм + ар + ная. BPE разбил его, потому что кошмарная не в train (только кошмарный). Но кошм + ар знакомы из кошмарный (negative), и Dense собрал negative из кусков.

Это и есть ценность BPE: кошмарная — новая форма (не в train), но модель обобщает через знакомые куски. Без BPE — <unk>, модель не может.

В предыдущей версии (без female-positive в train) восхитительная → восхи + т + и + тель + ная, и ная перевешивал в negative (потому что все female-формы в train были negative: ужасная, скучная). Dense выучил «female → negative», и ная сбивал восхи.

После добавления "это восхитительная картина" и "история была замечательная" в positive — Dense выучил, что female может быть positive. Теперь восхитительная → целое слово (BPE слил, потому что часто), и Dense уверенно positive.

Ключевой вывод: BPE помогает, но баланс данных — важнее. Без female-positive Dense выучил «female → negative» — неправильно. С балансом — правильно. BPE усиливает сигнал, но не заменяет данные.

```text
Пример: BPE-токенизация "кошмарная" → [кошм, ар, ная].

Embedding:
  E[кошм] = [0.2, -0.1, 0.5, ...]
  E[ар]   = [0.1, 0.3, -0.2, ...]
  E[ная]  = [-0.3, 0.4, 0.1, ...]

После энкодера: attention смешивает куски, и [CLS]-токен «видит» все три.
Dense: [CLS] → logits = [neg=2.5, pos=-1.2] → NEGATIVE.

Почему? Потому что "кошм" и "ар" знакомы из "кошмарный" (negative), и Dense выучил, что "кошм" + "ар" → negative.
"ная" — это "female-суффикс", но Dense **не** выучил "ная → negative" (если в train есть female-positive).
Поэтому "кошм" + "ар" перевешивают "ная", и результат — negative.
```


Подведём итоги
- Архитектура — энкодер + [CLS] + Dense. Проще, чем seq2seq: один вход, один выход, без декодера.
- [CLS] — специальный токен на позиции 0, чей выход после энкодера — агрегат всей фразы. TokenPooling(FIRST) берёт его.
- SoftmaxCrossEntropy — логиты, не вероятности. Accuracy — argmax по вектору.
- Проблема <unk> — без BPE слова вне словаря → <unk> → Dense уверенно врёт (bias, не сигнал). Пример: восхитительная, кошмарная → POSITIVE 1.00.
- BPE — разбивает слова на общие куски. кошмарная → кошм + ар + ная → Dense собирает negative из знакомых кусков. восхитительная → целое слово (часто в train).
- Баланс данных — важнее BPE. Без female-positive в train Dense выучил «female → negative», и ная сбивал восхи. С балансом — правильно.


## GPT-style language model

GPT — это только декодер без энкодера и cross-attention. 
Задача — предсказать следующий токен по предыдущим. 
Проще, чем seq2seq: один вход, одна голова, causal=true.


Все модели — от GPT-1 до GPT-4 — используют одну и ту же базовую архитектуру: декодер Transformer'а с causal=true. 
Масштаб, данные и пост-тренинг (RLHF) менялись, но механика осталась той же: Embedding → PE → DecoderBlock(causal) → TimeDistributedDense(vocab) → SequenceCrossEntropy.

[GptLanguageModelExample](../code/task/transform/GptLanguageModelExample.java)

```text
ВХОД:  flat(T) индексов
  │
  ▼ MaskingLayer(PAD)
  ▼ EmbeddingLayer(vocab, dModel)
  ▼ PositionalEncodingLayer
  ▼ TransformerDecoderBlock × M          ← Q = x, KV = x (self, causal!)
  │     (без cross-attention: encOut не нужен)
  ▼ seq(T, dModel)
  ▼ TimeDistributedDense(vocab)
  ▼ logits: seq(T, vocab)
  ▼ SequenceCrossEntropy по позициям
```

Единственное отличие от BERT-классификатора — causal=true и голова на каждую позицию, а не на [CLS].

causal=true означает: токен на позиции t видит только 0..t-1, но не t и не будущее. 
Без этого модель «подсмотрит» target на позиции t — на обучении loss упадёт до нуля, а на инференсе (где будущих токенов нет) развалится.

Как собрать «декодер без cross-attention»: 
собрать блок вручную из MultiHeadAttentionLayer(causal=true) + FFN.
```java
// Псевдокод: один GPT-блок
Functional.Node ln1 = b.layer(new LayerNormLayer.Dto(), x);
Functional.Node attn = b.layer(new MultiHeadAttentionLayer.Dto(HEADS, /*causal=*/ true), ln1);
Functional.Node x1 = b.add(x, attn);

Functional.Node ln2 = b.layer(new LayerNormLayer.Dto(), x1);
Functional.Node ffn1 = b.layer(new TimeDistributedDenseLayer.Dto(D_FF), ln2);
Functional.Node ffn2 = b.activation(ffn1, new Gelu(true));
Functional.Node ffn3 = b.layer(new TimeDistributedDenseLayer.Dto(D_MODEL), ffn2);
Functional.Node y = b.add(x1, ffn3);
```
x1 = x + Attention(LN(x)), y = x1 + FFN(LN(x1)). 
Тот же паттерн, что в TransformerEncoderBlock, только causal=true и без cross-attention.

GPT-блок = энкодер с causal=true
```java
//GPT-блок — это тот же блок, что в энкодере (self-attention + FFN + residual + LN), но с causal=true. 
//Это не «энкодер с causal» (энкодер — это часть seq2seq), а самостоятельный блок, который используется в GPT. У него нет cross-attention (потому что нет энкодера), и он не «часть seq2seq».
Functional.Node dec = TransformerEncoderStack.build(b, pe, new TransformerEncoderBlock.Dto(HEADS, D_MODEL, D_FF, DROPOUT, /* causal */ true), N_DEC);
```

Loss и метрика
```java
SequenceCrossEntropy loss = new SequenceCrossEntropy();
List<Metric> metrics = List.of(new TokenAccuracy());
```

- causal=true обязателен. Без него модель «подсмотрит» target на позиции t — на обучении loss упадёт, на инференсе развалится. TransformerEncoderBlock с causal=true — это и есть GPT-блок.
- TokenAccuracy как метрика. Считает argmax по каждой позиции, сравнивает с target. Стандарт для LM.

В стихах и прозе \n — это граница строки / строфы. Если его выкинуть, модель не выучит, где заканчивается строка, и будет генерировать «сплошной поток». \n — такой же токен, как слово, и он должен быть в словаре.

Но есть тонкость: если в корпусе много \n подряд (пустые строки между строфами), модель может «зациклиться» на них. Решение — схлопывать \n\n\n в \n\n при чтении (максимум две подряд — конец строфы). В коде — normalizeNewlines.

Для GPT — BPE обязателен. GPT-style LM на символьном уровне (каждый символ — токен) работает, но:
- словарь маленький (~100 символов), но последовательности очень длинные (SEQ_LEN = 128 — это всего 128 символов, ~20 слов);
- плохое обобщение — модель не видит связи между «кот» и «кота».

BPE решает оба: словарь ~500–2000 сабвордов, SEQ_LEN = 64–128 — это уже сотни слов, и «кот»/«кота» → общий префикс.

Сдвиг target: tgtIn = [BOS, w0, w1, ..., w_{N-2}], tgtOut = [w0, w1, ..., w_{N-1}, EOS]. 
На позиции t модель предсказывает tgtOut[t] = tgtIn[t+1] — следующий токен. causal = true гарантирует, что позиция t не подсмотрит tgtIn[t+1].

Цикл генерации: подать префикс → argmax последней позиции → добавить токен → повторить. 
Без KV-cache — O(T³) на всю генерацию, для SEQ_LEN = 64 — миллисекунды. 
В продакшене — KV-cache, O(T) на шаг.
Обучение даже уменьшенной GPT на 682 КБ — ~1 минута на эпоху, 40 эпох — ~40 минут. Без кэша каждый запуск — минуты. С кэшем — секунды.


### Генерация

Обученная GPT предсказывает следующий токен по префиксу. Генерация — цикл:
```java
List<Integer> ids = new ArrayList<>(bpe.encode(prompt));
ids.add(0, BOS);
for (int step = 0; step < maxTokens; step++) {
    int len = Math.min(ids.size(), SEQ_LEN);
    int[] input = ...;   // последние SEQ_LEN токенов
    float[] logits = model.forward(toFloat(input), false);
    int next = argmax(logits, (len-1) * vocab, vocab);
    if (next == EOS) break;
    ids.add(next);
}
```
Без KV-cache attention пересчитывается по всему префиксу на каждом шаге — O(T²) на шаг, O(T³) на всю генерацию. 
Для SEQ_LEN = 64 — миллисекунды. В продакшене — KV-cache, O(T) на шаг.

>Почему O(T³)? На шаге t генерации префикс имеет длину t, и attention считается по t × t матрице — O(t²). Суммируя по t = 1..T, получаем Σ t² = O(T³).
>
>С KV-cache: K и V для уже обработанных токенов сохраняются, и на новом шаге считается только Q для нового токена — O(t) на шаг, O(T²) на всю генерацию. Это на порядок быстрее.

Итого
- GPT — это декодер. Проще, чем seq2seq: один вход, одна голова, causal=true. История GPT — от 117M до триллионов параметров — это история масштабирования одной и той же архитектуры.
- Механика: Embedding → PE → DecoderBlock(causal) → TimeDistributedDense(vocab) → SequenceCrossEntropy. Сдвиг target, causal=true, TokenAccuracy — те же, что в seq2seq.
- Практика: BPE (для обобщения на формы), \n (для структуры), fallback кодировки (для реальных файлов), кэширование (для скорости).

#### Температура. Sampling

Если генерация берёт argmax на каждом шаге
```text
next = argmax_v logits[v]
```
Это детерминированно и жадно. На маленькой/недообученной модели это даёт два эффекта:
- Циклы. Если модель попала в состояние, где самый вероятный следующий токен — тот же, что только что был («не мог» → «не мог»), она из него не выйдет никогда. Генерация не умеет «рискнуть» и выбрать второй по вероятности токен.
- Вырождение. Генерация выбирает моду распределения. Если мода — PAD или частый служебный токен, вывод состоит из них. Реальное разнообразие модели (хвост распределения) не видно.

Sampling решает обе проблемы: он сэмплирует из распределения, а не берёт argmax, и модифицирует распределение, чтобы отсечь мусор.

Логиты → вероятности через softmax с температурой T:
$$
p_v = exp(z_v / T) / Σ_u exp(z_u / T)
$$
z_v — это «логит» (logit) токена с индексом v. То есть сырое, необработанное число, которое выдаёт модель для токена v на последнем слое, до превращения в вероятность.

p_v - вероятность взять логит z_v как следующее слово в генерации

- T = 1 — исходное распределение модели.
- T < 1 — распределение острее: z_v / T растягивает разницу между логитами, максимум становится ещё более доминирующим. При T → 0 sampling вырождается в greedy.
- T > 1 — распределение площе: разница сглаживается, редкие токены получают больше шансов. При T → ∞ — равномерное распределение.


Top-k

Оставляем только k токенов с наибольшими логитами, остальным ставим -inf (после softmax — вероятность 0).

Зачем: даже после temperature в хвосте распределения остаются тысячи токенов с крошечными, но ненулевыми вероятностями. Суммарно они дают заметную массу — и sampling может «выстрелить» в мусорный токен. Top-k жёстко отсекает хвост: k=40 означает «выбираем только из 40 лучших».

Ограничение top-k: он фиксированный. На «плоском» распределении (модель не уверена) 40 токенов — это почти весь сигнал, хвост и так мал. На «остром» (модель уверена) 40 токенов — это уже мусор, надо было бы оставить 3–5. Top-k не адаптируется.

Top-p (nucleus sampling)

Вместо фиксированного числа токенов оставляем минимальный набор, чья кумулятивная вероятность ≥ p
```text
отсортировать p_v по убыванию
накопить сумму, пока ≥ p
отрезать хвост
перенормировать
```

Зачем: top-p адаптивен. На «остром» распределении (модель уверена) он оставит 2–3 токена. На «плоском» (модель не уверена) — 50–100. Это ровно то поведение, которое нужно: доверять модели, когда она уверена, и давать свободу, когда нет.

Top-k + top-p вместе: top-k сначала жёстко режет до 40 кандидатов (защита от совсем мусорных токенов), top-p потом адаптивно сужает внутри этих 40. Порядок важен: top-k до softmax, top-p после (top-p работает с вероятностями).

Repetition penalty

Идея: понизить логиты токенов, которые уже встречались в недавнем окне. Чтобы модель не залипала на одном и том же сильно вероятном "мог" или "что".
```text
если logit > 0:  logit /= penalty
если logit < 0:  logit *= penalty

Почему так, а не просто logit -= penalty?

Положительные логиты делятся — большие становятся меньше, но остаются положительными. Пропорционально, а не аддитивно.
Отрицательные умножаются — становятся ещё более отрицательными. Тоже пропорционально.
```

Окно REPETITION_WINDOW = 32: штрафуем только последние 32 токена. Если штрафовать всё с начала, модель не сможет естественно повторять слова (а в стихах повторы — норма). 32 — компромисс: ловит локальные циклы, не мешает дальним повторам.

Стандартная практика — штрафовать уникальные.

## Где KV-cache ускоряет

KV-cache — это только инференс. 
На обучении модель видит весь target сразу (teacher forcing), и attention считается один раз по всей последовательности. 
На инференсе (авторегрессия) модель генерирует по одному токену за шаг, и без кэша каждый раз пересчитывает attention по всему префиксу.
